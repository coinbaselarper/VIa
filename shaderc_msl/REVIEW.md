# Review of gta6rt_shaderc_msl (round 1)

Date 2026-11-26. Reviewer rebuilt in `port/build/review-shader-toolchain-{arm64,x86_64,subdir-arm64}`, re-ran the ctest suite with Metal API and shader validation, recomputed counts from `port/build/shaderc_msl/runs/main/{results.jsonl,manifest.tsv}` and `cas/`, and wrote independent probes (scratch area, not kept in the module). Nothing under `port/shaderc_msl` or `port/build/shaderc_msl` was changed. The machine was loaded by other agents during the review (load average 7-10), so my timings are not clean.

Verdict: APPROVED_WITH_FIXES. The toolchain does what the report says for the counts that can be recomputed, and the main correctness claims held up under my probes. There are two blocking defects, both in how results reach the backend or how a test was run, and several claims that are worded more strongly than the evidence.

## Blocking

1. **`Catalog::load` silently drops 589 built shaders.** `src/catalog.cpp` treats every line whose first character is `#` as a comment. 589 shader names begin with `#` (209 ms, 338 ps, 42 vs), for example `#FSColor2FullBevel_d17d2c71_Wrapped` (Scaleform UI pixel shaders, i.e. first-scene shaders). The manifest has 19,852 rows; `shaderc_msl_catalog_test` prints `catalog: 19263 shaders`. The test passes because its 4 pairs are `!`-prefixed names and nothing compares the loaded count to the manifest. The backend cannot `find()` those 589 shaders. Fix: treat only the two header lines (`# `) as comments, or escape names; add an assertion `catalog.size() == number of data lines`.
2. **Two ctest tests abort under Metal validation.** `shaderc_msl_vs_lane_identity` and `shaderc_msl_vs_lane` die with `Texture at colorAttachment[0] has usage (0x01) which doesn't specify MTLTextureUsageRenderTarget` (the render target is created without `rtd.usage = MTLTextureUsageRenderTarget`). With that one line added in a scratch copy, both pass under `MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1`: identity 12/12 cases, vs_lane 40/40 lane == kernel, 0 GPU errors. So the reported results stand, but the tests as shipped are invalid under validation and the report did not say they were only run without it. Fix the two texture descriptors.

## Recomputed and confirmed

- Built set: 19,852 rows in `manifest.tsv` (main ps 8,993, ms 7,156, vs 1,438, cs 1,839; library cs 424; exe 2), all 19,852 metallibs exist, 12,186 metallibs / 3.12 GB in `cas/`. `results.jsonl` has 19,857 rows, 2 of them early `metal_fail` rows that were rebuilt. Corpus stage sizes (vs 2,236, ps 12,101, cs 2,689, ms 9,282, gs 195 = 26,503) match index.json.
- Recipe is current: for 600 random manifest shaders the content key recomputed with today's tools equals the manifest key (0 mismatches). I also rebuilt 48 stratified shaders (ps 16, ms 16, vs 8, cs 8) into a scratch store: all 48 metallibs are byte-identical to the stored ones.
- Throughput: from `results.jsonl`, non-cached rows between 04:49 and 05:36 are 8,122 (ps 4,432, ms 2,866, vs 816, cs 8), i.e. 10,369/h over the window, 10,534/h first-to-last row. This reproduces the 10,435/h claim. (Note: 7,504 of 19,857 rows are cached replays; any count of rows per hour must exclude them, the report's figure does.)
- Peak RSS: median 94 MB, p99 977 MB, max 5,865 MB for `metal` (report: 82 / 930 / 5.9 GB); consistent.
- `-O0` fallback fired once (ScreenProbes_ActivateRays, before `noinline_hot_helpers`), as reported.
- Manifest versus index.json for all 19,852: every manifest table/array binding is a member of the shader's index.json bindings, no two share a buffer index, push buffer never collides, push block present iff `push_constant_bytes > 0`. 2,817 shaders list fewer bindings than index.json (ms 1,845, cs 509, ps 289, vs 174): SPIRV-Cross drops unused variables, consistent with the report's "dead bindings" remark (14% here, 15% in its sample). Descriptor arrays sit at buffer index b+2 in 779 cs rows, consistent with the plain-buffer finding.
- Reflection probe of my own (compute only, 150 random built cs outside the builder's sample, `MTLPipelineOptionBindingInfo|BufferTypeInfo`): 40 shaders (a first run of 150 hung on one compute pipeline build for over 30 minutes on the loaded machine and was killed; I did not identify which shader, so a hang in a Metal pipeline build for some corpus compute shader is possible but unattributed). All 40 pipelines reflected: 202 tables, every one at the manifest's buffer index with all struct members at offset 0, no reflected `spvDescriptorSet*` buffer missing from the manifest, no manifest table outside index.json. This supports the binding claim for cs; I did not re-probe ps/vs/ms reflection.
- Mesh dead-output elimination, independent check: for 250 random step-1/2 mesh shaders I parsed the paired pixel shaders' SPIR-V with `spirv-dis` and checked that no input location actually read (any use other than declaration/decoration) is in the mesh shader's dropped list, using the pairs.json records and digest aliases: 0 violations. Step counts recomputed from `mesh_fit.jsonl`: 4,631 over limit = 3,408 + 122 + 1,051 + 50; 401 of them over 124 scalars. `mesh_pso.jsonl`: step 0 300/300, step 1 2,811/2,811 OK, step 2 36 OK / 49 FAIL; `mesh_split64.json` 191 OK / 9 fail. All match.
- GS census, independent check: I computed the HASH digest of all 195 `GS_VoxelizeGeneric` DXBC containers and searched the 275,540,780-byte decoded pipeline library for the 16-byte digests: 0 of 195 found anywhere (positive control: 210 of 300 random corpus pixel shaders found). The strings `Voxeliz` / `GS_Voxel` also occur 0 times. This confirms "0 of 195 in the library" without relying on the stage-slot parser.
- fp64: the 5 shaders' f64 values are only produced by OpFAdd/OpFSub/OpSelect/OpBitcast and consumed by OpFOrdLessThan/GreaterThan, OpIsNan, OpIsInf, OpFConvert and OpBitcast. No multiply, divide, or conversion into f64 exists, so the operations soft_f64 covers are the complete set. `shaderc_msl_soft_f64` passes under validation (4,194,304 cases, 0 mismatches).
- Builds: arm64 and x86_64 (Mach-O x86_64 verified) configure and build clean; `add_subdirectory(/.../port/shaderc_msl)` from a throwaway parent builds the library and probe. ctest without validation is not what I ran; with validation: soft_f64 pass, catalog pass, the two vs tests as above. No x86_64 binary was run (same as the builder).
- Disk: 124 GiB free after my work (rule: 60).

## Claims that are weaker than stated (non-blocking, fix the wording or the data)

1. **"No loss from parallelism" is not demonstrated.** The evidence is 3.94-3.98 job-seconds per wall second at 4 jobs, but per-shader `total_s` is wall time measured under the same contention, so that ratio is about 4 by construction. No 1-job baseline on the same shaders is in STATUS. My own 1-job versus 4-job runs of the same 48 shaders gave 17.7 s versus 10.1 s wall (1.75x) and per-shader time doubled, but the machine was loaded by other agents, so I cannot call that a scaling loss either. The 4.9 h projection ("ideal scaling") is therefore an unmeasured upper bound on speed. The 10,435/h itself is real.
2. **Per-stage "0 failing" rows extrapolate to shaders never built.** Of the spike/s5.2 baseline failures, only part were built by this batch: ps atomics 523 of 1,017, vs subgroup 730 of 1,252, cs atomics 9 of 20 (counts from `step1.jsonl` + `supp207.jsonl` against the manifest). The rest (494 ps, 522 vs, 11 cs) are unbuilt with the new recipe. The spike showed the 1,017 ps compile with MSL 3.1, but the vs lane route compiled only 730 of 1,252. The table rows "vs 0", "ps 0" and the "about 1,369 (5.2%)" total count unbuilt shaders as passing. The report does list 7,077 unbuilt, but STATUS section 7 should state the built fraction per row.
3. **"50 exceed the scalar limit even after steps 1-2" is wrong as worded.** All 50 have `records == 0` (no pipeline-library record), so steps 1-2 were never applied to them: 126+ scalars is the as-translated count. Same for 926 of the 1,051 split64 shaders. Only 125 paired shaders (plus 49 measured step-2 failures and about 21 unmeasured) truly need a split after dead-output elimination. For the 976 unpaired ones the real answer is unknown until pipeline creation.
4. **Manifest omits shaders the report counts as fixed.** The 24 LDS-shrunk cs (only 4 are in `manifest.tsv`), the 5 fp64 cs (0), and 3 of the 7 huge kernels (the `Art`, `Irt`, `Urt` RTShadowTrace ones) were built into `cas/` by `cs_check.py` but are not in the manifest, which `batch.py` writes from `results.jsonl`. The backend cannot find them until the batch is resumed. The report's "19,852 built" does not include them. The three huge ones in the manifest do point at the `noinline_hot_helpers` keys that built a pipeline.
5. **Stale numbers in STATUS section 6.** The cs row (mean 9.10 s, sum 16,727 s, max 617 s) includes superseded rows; `summary.json` and the CAS rows give mean 8.68-8.74, sum 15,964-16,067, max 442-445 s. Projection is 68,385 job-s in `summary.json` versus 70,500 in STATUS. Small, but the headline table does not match the files.
6. **Order claim.** The report says builds start with the 430 shaders the logs show. In the recorded run the first rows are the UI shaders (`!FSGradFullBevel...`) and the 426 library/exe shaders were built at 11:19, after about 15,000 others. The runtime-first ordering exists in `batch.py` but was added after the first session. UI-first, as the task asked, did happen.
7. **Hang risk.** The 3 vertex shaders that hang the GPU on synthetic data are `VS_Transform_PositionOnly_*` and `VS_TransformEntityMask_*`, i.e. common transform shaders, not exotic ones. The report says real data may or may not trigger it; I agree it is unknown, but this is the one open item most likely to hurt rendering, and the kernel route is the fallback. I did not rerun the hangs.
8. **Mesh route flags.** `mesh_route=hw` is set for the 597 unmeasured step-1 shaders (the measured rate was 2,811/2,811) and for the 37 unmeasured step-2 shaders (measured rate 36/85, so about 21 of those 37 will fail). Also `mesh_as_compute` appears nowhere in the manifest because only built shaders are listed.
9. **Split-64 check is a shape check only.** "191 of 191 accepted" shows Metal accepts a 64-vertex declaration for a body that still writes 128; it says nothing about a correct split (the report states the split is unimplemented).
10. **`shrink_lds` rests on the RSRC2 LDS_SIZE decode** (`((rsrc2 >> 15) & 0x1FF) * 512`) and was never checked against the SPIR-V's actual LDS accesses or run on data. Pipelines build; behaviour is unverified. Out-of-allocation reads return unspecified values on Metal.
11. **Pairing-derived variants are only valid for the library's pixel shaders.** Dead-output elimination (step 1) and trimming (step 2) were validated here against library pairs only (my probe confirms that); a runtime-created pairing with a different pixel shader needs a new variant, as `patches/mesh_outputs.md` says. Depth-only records (3,517 mesh shaders paired with no pixel shader) drop every user output.
